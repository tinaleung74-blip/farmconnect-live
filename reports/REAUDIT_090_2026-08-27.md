# Re-audit after migration 090

Verdict: NOT READY to claim complete workflow reliability. Three actionable defects remain in the recent changes.

Scope: local source review, existing regression tests, and one mocked execution of the actual support component. No live requests, database writes, or application fixes performed in this audit. User supplied migration 090 verification; it confirms function existence, not end-to-end correctness.

## 1. High: a recovered payment can be submitted again

Evidence: lib/farmconnect-v1.tsx:5310-5320, 5290, 5453; database/applied/009_manual_payment_review_flow.sql:108-129; database/applied/044_workflow_chain_guard.sql:223-240.

Reproduction from code: a payment commits but its response is lost. Retry finds source_record_id, sets submittedId, removes the pending key, and returns without leaving the page. The form remains filled and Submit remains available. Another click creates a new operation key. The underlying payment function flags repeated references as possible_duplicate but still inserts a new request.

Impact: duplicate review requests. This is NOT proof of a duplicate payout or wallet credit; downstream approval behavior was not executed.

Fix direction: treat recovered success as terminal, disable submit based on submittedId, clear/leave the form, and retain/reconcile operation identity until the user starts a genuinely new payment. Test the exact recovery → click again sequence.

## 2. Medium: support can remain locked in Retry permanently

Evidence: lib/support-conversation.tsx:57-68, 84. A pending draft is cleared on explicit SQL rejection only when !pending. Once the draft is restored or already pending, the same definitive rejection retains it and the textarea remains disabled.

Confirmed using the transpiled component with mocked React state and RPC returning P0001/INVALID_MESSAGE for a restored pending draft:

```
pendingStillLocked: true
pendingSaved: true
note: Message not confirmed. Retry safely using the same message.
```

Impact: the user cannot correct the message or send a different one. This was a mock reproduction, not a production incident.

Fix direction: distinguish uncertain delivery from definitive rejection. Reconcile the operation receipt on the server before releasing the draft/key. Do not blindly clear all network errors because the original request may have committed.

## 3. Medium: onboarding bypasses the KYC form's pending-state gate

Evidence: lib/farmconnect-v1.tsx:5759, 6003-6021, 6076, 6166-6183, 6519.

Normal Settings uses openPanel to stop opening KYC when pending. New onboarding initializes activePanel directly to kyc and keeps it there after successful submission. The Send button checks only consent/submitting. submitKyc does not check pending/approved/error state. Uploaded files remain selected after success.

Impact: a user can immediately send again while under review, or submit from the onboarding route while status should block it. New upload folders and consent calls occur before the KYC RPC. Whether the live RPC rejects, overwrites, or otherwise handles the duplicate is unverified because its full definition is not checked in.

Fix direction: enforce allowed UI states (not_submitted/rejected), show Under review/Verified instead of the form, guard the handler, and independently verify the server transition rules. Reuse uploaded paths and reconcile uncertain submissions rather than re-uploading on every retry.

## Additional verification gaps, not confirmed exploits

- SQL 090 checks role and operation identity but delegates session ownership/account rules to existing support RPCs. Their full definitions and live RLS must be inspected before declaring authorization sound.
- KYC UI collects a full ID number but passes it as p_id_number_last4. The live function's interpretation must be verified; its reference declaration alone cannot establish whether this is accepted or rejected.
- Missing isolated database configuration still prevents safe end-to-end write testing. Do not disable the production-write guard just to obtain a green test.

## Tests

Existing delivery-state and care-report-draft tests: 8/8 PASS. Those tests do not cover the payment recovery second-click or onboarding status transitions. The support failure mock above exposes an untested case despite that green result.

Recommended fix order: payment terminal state → support rejection recovery → onboarding KYC state gate → role-separated isolated end-to-end tests.
