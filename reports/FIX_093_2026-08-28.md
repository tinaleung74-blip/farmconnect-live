# Support fixes — 2026-08-28

## What changed

- KaFarm replies are generated in `/api/support/reply`, using the saved message and authenticated user. The browser sends only an operation key. Existing reply rules remain in use; customers cannot supply a system reply, role, or actor.
- SQL 093 disables the old arbitrary-text reply function. Its replacement is service-role-only, checks the saved operation and current chat state, and records one reply ID per operation under a lock. A replay cannot create another automatic reply. Closed/escalated chats do not receive a new rule reply.
- Support provides Retry loading and retries initialization on the browser online event. Valid uncertain submissions retain their original key.
- Damaged drafts no longer prevent viewing the conversation. Sending stays blocked until explicit, confirmed recovery. Recovery keeps the original in a separate localStorage entry, opens an empty draft, and sends nothing automatically. A user is warned to inspect history because a damaged draft's previous delivery cannot always be established.

## Deployment requirements — not applied by this task

1. Use an isolated database with 090-092 applied. Configure the app server with `SUPABASE_SERVICE_ROLE_KEY` for that SAME project, plus the public URL/anon key. Never put the service key in a NEXT_PUBLIC variable or share it in chat.
2. Apply `database/applied/093_support_trusted_replies.sql`. Expected verification: authenticated/anonymous write privileges false; server write privilege true; business_records_changed false.
3. Deploy the matching API and frontend together. Applying SQL first intentionally blocks automatic replies in an old frontend; user support submissions remain separate. There is no unsafe fallback to the old RPC. A missing server key causes an explicit unavailable response, not a forged reply.
4. On the isolated target, test customer and caretaker sends; repeat the same reply operation; attempt arbitrary reply text and someone else's receipt; close/escalate during reply generation; interrupt initial loading; recover a damaged draft. Then coordinate production rollout.

This task does not execute production SQL, push, or deploy. Existing rows are not rewritten by 093; the new reply ID column is nullable for historical operations. Old untracked replies are not automatically deduplicated/backfilled.
